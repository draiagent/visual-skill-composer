# 核心概念

## 五個層級

VSC 固定用五個問題、固定的順序，因為每一個答案都會收斂下一個。

1. **專案包（Project pack）**——你要做什麼。決定下面所有層級的預設值。
2. **技能（Skills）**——這件事需要哪些能力。由專案包預先勾選，再由你增減。
3. **風格包（Style pack）**——色彩、字級、圓角，以及一份明確的「該避免什麼」清單。
4. **品牌包（Brand pack）**——套誰的品牌識別，這裡只放參照，不放品牌本體。
5. **品控包（QA pack）**——要跑哪些檢查、通過門檻多少、允許重跑幾次。

順序反過來是走不通的。你還不知道要做儀表板還是漫畫筆記之前，
根本沒辦法合理決定品質門檻要訂在哪裡。

## 這是「包」，不是「設定」

一個包就是一份帶有明確主張的小檔案。`style-packs/swiss-editorial.yaml`
不只是列出色碼——它同時列出這個風格**禁止**什麼（漸層、投影、裝飾性圖示）。
會遵守 avoid 清單的執行端，做出來的東西才會真的像瑞士風格；
忽略它的執行端，做出來的就跟其他所有東西長得一樣。

## 是「推薦」，不是「自動化」

專案包把技能標記成 `recommended_skills` 或 `suggested_skills`。
推薦的會預先勾選，建議的會附上理由讓你自己決定。
系統不會偷偷加東西，每一個選擇都保持可編輯。
最後帶走的那一組，一定是使用者自己選的。

## 相依關係

`registry/skills.json` 裡每個技能都有 `requires`。
`brand-check` 需要 `brand-system`，因為你不可能去比對一套從來沒載入的品牌；
`auto-repair` 需要 `vision-judge`，因為修正必須有東西可以對照。
如果組裝器產出一組相依沒補齊的技能，那份 manifest 根本跑不起來。

## ID 是英文，標籤才是資料

所有 ID 一律英文 kebab-case，永遠不翻譯；
中英文標籤是欄位資料，顯示的時候才解析。
正因如此，一個人可以全程用繁體中文組裝，
產出的東西照樣能交給 runtime、CI 流程，或只讀英文的協作者。

## 組裝不等於執行

VSC 產出 manifest 就停手。它不渲染、不呼叫模型、不寫任何素材。
執行是 VAD 或任何看得懂這份 schema 的 runtime 的工作。
把兩者切開，才讓這份 manifest 能同時在 Claude Code、Codex、Gemini CLI 與 CI 之間流通。
